📚 الدروس المستفادة (محدثة)

أ. دروس تقنية (اكتشفت أثناء التنفيذ)

L1: persist يقرأ التخزين قبل عرض المكونات

· progressStore و highScoreStore تُنشأ عند استيراد الملف، قبل AppGate.
· لذلك اختيار الوضع يجب أن يسبق الاستيراد، أو نُعيد التحميل بعد الاختيار.
· الحل المنفذ: AppModeSelection يحفظ soroban_mode ثم window.location.reload().

L2: البادئة وحدها لا تكفي

· بادئة local:/cloud: تفصل المفاتيح، لكن بدون memoryStorage للزائر (لو كان موجوداً)، لا يمكن ضمان "عدم الحفظ".
· قرار: لا يوجد وضع زائر. الأوضاع: محلي / سحابي فقط.

L3: maskName في السيرفر يجب ألا يثق بالعميل

· child_masked_name قابل للتعديل من المستخدم → لا يصلح للعرض.
· الحل: applyLocalIdentity تقرأ من soroban_hero_key (محلي)، لا من user_metadata.

L4: signInWithPassword يُنشئ جلسة جديدة

· استدعاؤه من Guardian يجدّد الجلسة.
· يجب ألا يُستدعى loginParent (الذي يستدعي adoptUser → قد يمسح cloud: data).
· الحل: استدعاء supabase.auth.signInWithPassword مباشرة، ثم cloudSync.getSession() لاستعادة الهوية.

L5: handleBackToRole لا يصلح لتجاوز RoleSelection

· تعديله ليذهب لـ HeroDashboard مباشرة يمنع الوصول لـ GuardianDashboard.
· الحل: handleBackToRole يبقى أصلياً، وRoleSelection.handleSelect يتحقق من getMode().

L6: handle_new_profile محمي بـ EXCEPTION قد يخفي أخطاء

· EXCEPTION WHEN OTHERS THEN NULL يمنع فشل التسجيل، لكنه يُنشئ صفوفاً بـ display_name افتراضي وshow_on_leaderboard = TRUE.
· هذا لا يكسر السحابي، لكنه ثغرة قبل الإطلاق العام: يجب تعديل الدالة لتعتمد على consent_leaderboard، أو إضافة check على display_name (يجب ألا يكون NULL).

L7: handleReset بحاجة إلى قائمة بيضاء معكوسة

· keysToKeep الحالية تحتفظ بالأرشيف القديم وتمسح local:/cloud:.
· الإصلاح: استبدالها بـ isSafeToExport (المعكوس): احتفظ بـ sb-* و soroban_mode و soroban_hero_key، وامسح الباقي.

L8: handleBackup القديم كان يسرّب الجلسة

· localStorage كاملاً = sb-* + soroban_progress_owner + أسماء حقيقية.
· الإصلاح: قائمة بيضاء (local:/cloud:/مفاتيح جهاز محددة).
· تنبيه: أي ملف JSON قديم (sorobanmind-backup-2026-11-10.json) يحتوي على جلسة حقيقية. يجب حذفه فوراً.

L9: avatar_id لا يمكن إرساله للسحابة قبل SQL

· heroNames.ts (30 اسماً) لا تطابق avatars.ts (100 شخصية).
· إرسال avatar_id = heroKey سيضع قيمة غير موجودة في public_profiles (بعد SQL).
· الحل المؤقت: لا نرسل avatar_id. عند تنفيذ SQL، نضيف check على القيمة.

L10: soroban_hero_key و soroban_child_name هوية جهاز

· لا بادئة local: أو cloud:.
· AppGate يكتبهما مباشرة.
· السبب: الاسم المختار هو هوية الجهاز، لا هوية الوضع.

ب. دروس منهجية (عملية)

L11: تعدد المساعدين يُنتج تناقضاً

· 4 مساعدين (أنا، كلاود، GPT، زميل) قدموا خططاً مختلفة.

L18: البيئة السورية تتطلب "لا بيانات شخصية"

· child_name في Supabase = مخاطرة قانونية (12/2024).

L19: PWA هو الخطوة التالية قبل الإطلاق

· التطبيق على GitHub Pages، لكنه ليس "قابلاً للتثبيت".
· التوصية: manifest.json + sw.js + vite-plugin-pwa قبل الإطلاق العام.
