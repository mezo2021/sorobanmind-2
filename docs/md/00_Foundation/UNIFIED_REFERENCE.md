# 2. القرارات المعمارية الكبرى — Architectural Decisions

هذه القرارات هي المرجع الملزم عند تصميم أي تعديل لاحق. لا يجوز تغييرها ضمن إصلاح جزئي دون قرار معماري صريح وموثق.

## 2.1 قفل تدفق المصادقة والتبنّي — Authentication & Adoption Locking
يعتمد تدفق المصادقة والتبنّي على آليتي حماية متكاملتين:

- `authFlowInProgress`: يمنع تداخل عمليات المصادقة داخل التبويب نفسه.
- Web Locks: تنسّق العمليات المتنافسة بين التبويبات باستخدام قفل مشترك.

لا توجد آلية مستقلة باسم `adoptionInProgress` في التنفيذ الحالي؛ كان هذا المتغير جزءاً من تصميم سابق، ثم أُلغي قبل اعتماد التنفيذ الحالي.

اسم القفل المعتمد:

`soroban-auth-adoption`

الهدف هو منع سباقات المصادقة والتبنّي، وعدم السماح ببدء عملية اعتماد متعارضة قبل اكتمال العملية السابقة بأمان.

عند عدم توفر القفل أو انشغاله، لا يجوز اعتبار العملية ناجحة؛ تتم معالجة الحالة وفق رمز الخطأ المعتمد `AUTH_FLOW_BUSY`.

## 2.2 سياسة LOCAL WINS

عند تسجيل الدخول بالحساب نفسه، تكون الأولوية للبيانات المحلية وفق سياسة `LOCAL WINS` المعتمدة.

- لا يؤدي تسجيل الدخول أو تبنّي الحساب إلى استبدال التقدم المحلي تلقائياً ببيانات سحابية.
- لا يُفقد التقدم الموجود على الجهاز بسبب عملية اعتماد الحساب.
- يجب الحفاظ على اتساق هوية الحساب ومنع الخلط بين بيانات حسابين مختلفين.
- وجود `OWNER_KEY` وحده لا يبرر استعادة تقدم سحابي تلقائياً عند فقد البيانات المحلية.

هذه السياسة تخص مسار تسجيل الدخول واعتماد الحساب، ولا تلغي الاستعادة اليدوية التي لها مواصفة منفصلة.

## 2.3 سياسة الاستعادة — Restore Policy

تعتمد عمليات الاستعادة على الاستبدال الكامل ضمن نطاق البيانات المحدد للعملية، وليس الدمج الانتقائي غير المنضبط.

الآليات المعتمدة:

- `handleRestore`: استعادة ملف JSON وفق قائمة المفاتيح المسموح بها (Whitelist).
- `loadFromCloud`: استعادة بيانات التقدم السحابية ضمن النطاق المحدد للعملية.

القرارات:

- لا تُنشأ آلية استعادة انتقائية موازية.
- تتطلب الاستعادة اليدوية تأكيد المستخدم.
- يتم أخذ Snapshot قبل الاستبدال في المسارات التي نصت مواصفاتها على ذلك.
- يجب توفير Rollback عند الفشل وفق مواصفة كل عملية.
- لا يجوز الخلط بين الاستعادة اليدوية وسياسة `LOCAL WINS` الخاصة بتسجيل الدخول.

## 2.4 إدارة أخطاء المزامنة — CloudSyncError

تعتمد أخطاء المزامنة على نوع خطأ واضح هو `CloudSyncError` بدلاً من التعامل مع جميع حالات الفشل كأخطاء عامة.

- تُترجم الأخطاء المعروفة إلى رسائل مفهومة للمستخدم في `AuthModal.tsx`.
- يجب الحفاظ على التمييز بين حالات المصادقة والمزامنة والاستعادة.
- لا يجوز إخفاء فشل عملية حساسة أو تحويله إلى نجاح ظاهري.
- يجب ألا تظهر رسالة نجاح أو يحدث Reload قبل اكتمال العملية التي تعلن نجاحها.

## 2.5 التحقق من وضع التطبيق — App Mode

يُستخدم `getMode()` من `src/utils/appMode.ts` للتحقق من وضع التشغيل الحالي:

- `local`
- `cloud`
- `null` عند عدم وجود وضع صالح أو تعذّر قراءته.

يجب أن تحترم عمليات القراءة والكتابة والحذف وضع التشغيل، وألا تختلط مساحة Local بمساحة Cloud.

المفاتيح المعزولة تستخدم البادئات:

- `local:`
- `cloud:`

لا يُضاف `userId` إلى مفاتيح التخزين المحلي.

## 2.6 حماية هوية الطفل وبياناته

القرارات المعتمدة:

- لا تُرسل أسماء الأطفال الحقيقية إلى Supabase ضمن التصميم الحالي.
- لا يُستخدم `user_metadata` لتخزين اسم الطفل الحقيقي.
- لا يُحذف تقدم الطفل أو شهاداته ضمن إصلاح لا ينص صراحة على ذلك.
- عمليات Reset وLogout يجب أن تحذف فقط المفاتيح التي يحددها نطاق الإصلاح المعتمد.
- لا تُعامل هوية البطل أو اسم الشخصية بوصفها اسماً حقيقياً للطفل.

## 2.7 حدود الملفات المجمدة

الملفات التالية مجمدة ضمن الخطة الحالية:

- `src/App.tsx`
- `src/utils/storage.ts`

لا يتم تعديلهما ضمن البنود المعتمدة حالياً.

إذا أثبت الفحص أن إصلاحاً لا يمكن تنفيذه بأمان دون أحدهما، يجب إيقاف التنفيذ وتوثيق السبب والاختبارات المتأثرة، ثم طلب اعتماد مستقل قبل التعديل.

# 8. استراتيجية Commits والتراجع

## 8.1 قاعدة Commit

كل Commit يمثل وحدة إصلاح مستقلة ومكتملة وقابلة للاختبار والتراجع.

| الحالة | طريقة التنفيذ |
|---|---|
| إصلاح ملف واحد | تعديل ← Commit ← Build ← اختبار |
| إصلاح ملفين مترابطين | تعديلهما معاً ← Commit واحد ← Build ← اختبار |
| إصلاحات مستقلة متعددة | Commits منفصلة |
| فشل Build | إيقاف العمل |
| فشل اختبار وظيفي | إيقاف المرحلة وتشخيص السبب |

## 8.2 نقاط الرجوع

قبل كل مرحلة:

- التأكد من وجود نسخة مستقرة في GitHub.
- تسجيل Commit الحالي بوصفه نقطة رجوع.
- الاحتفاظ بنسخة أصلية من الملفات التي ستتغير عند الحاجة.
- عدم إجراء تعديلات متوازية خارج نطاق المرحلة.

## 8.3 التراجع

يعتمد `git revert` للتراجع عن Commit معتمد عند الحاجة، مع الحفاظ على تاريخ المشروع.

لا يستخدم Reset أو حذف بيانات المستخدمين لمعالجة فشل إصلاح برمجي.

التراجع عن الكود منفصل عن التعامل مع بيانات المستخدمين.

- إذا اختلف الكود الحالي عن الأرشيف، يتوقف التنفيذ مؤقتاً وتتم مراجعة التصميم المتأثر.
- لا يتم تطبيق افتراض قديم على كود جديد دون تحقق.
- يجب التأكد من المسارات الفعلية ونقاط الاستدعاء، لا الاكتفاء بتشابه أسماء الملفات.
