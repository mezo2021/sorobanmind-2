## 4. استراتيجية التراجع العامة

نعتمد Git بوصفه وسيلة التراجع الأساسية، مع تسجيل نقطة رجوع واضحة قبل كل مرحلة.

### قبل كل مرحلة

- التأكد من وجود نسخة مستقرة في GitHub.
- تسجيل Commit الحالي بوصفه نقطة الرجوع.
- عدم إجراء تعديلات متوازية خارج نطاق المرحلة.
- الاحتفاظ بالنسخة الأصلية من الملفات التي ستتغير، للمقارنة عند الحاجة.
- عدم حذف بيانات المستخدمين بغرض معالجة خطأ برمجي.

### التعامل مع الفشل

| ما حدث | الإجراء |
|---|---|
| فشل Build | إيقاف العمل وعدم الانتقال إلى الملف التالي |
| خطأ في Zustand أو التخزين | تحديد ما إذا كان سببه التعديل أم سلوكاً سابقاً |
| فشل تسجيل الدخول | إيقاف اختبارات الحسابات الحقيقية وتشخيص المسار |
| ظهور بيانات حساب سابق | إيقاف اختبارات تبديل الحسابات فوراً |
| فشل الاختبار الوظيفي | عدم اعتماد Commit بوصفه إصلاحاً ناجحاً |
| فشل الإصلاح بعد Commit | استخدام `git revert` للـ Commit المعني |

### لماذا Git Revert؟

لأنه ينشئ Commit عكسياً يحافظ على تاريخ المشروع، ويسمح بتحديد الإصلاح الذي تم التراجع عنه وسبب ذلك.

> التراجع عن الكود لا يعني حذف بيانات المستخدمين أو إعادة ضبطها. التعامل مع البيانات منفصل عن التراجع البرمجي.

```ts
export const LEGACY_CHARACTER_MAP: Partial<Record<string, CharacterType>> = {
  fox: 'sham',
  owl: 'bana',
  rabbit: 'rayan',
  panda: 'joud',
  aya: 'joud',
};
```

لكن `HeroDashboard.tsx` يحتوي خريطة محلية مكررة لا تتضمن `aya`:

```ts
const LEGACY_CHARACTER_MAP: Record<string, CharacterType> = {
  fox: 'sham',
  owl: 'bana',
  panda: 'joud',
  rabbit: 'rayan',
};
```

`CharacterSelector.tsx` يستخدم الخريطة المشتركة من `types.ts`، بينما يستخدم `HeroDashboard.tsx` نسخته المحلية.

#### أثر الاختلاف

إذا كانت قيمة التخزين القديمة `soroban_companion = 'aya'`:

- يستطيع `CharacterSelector` تحويلها إلى `joud`.
- لا يتعرف عليها `HeroDashboard` في الخريطة المحلية.
- ينتقل `HeroDashboard` إلى مسار القيمة غير المعروفة، ويكتب `sham` بدلاً منها.
- بذلك تضيع نتيجة التحويل القديمة `aya → joud` في هذا المسار.

#### القرار المعتمد

أقل إصلاح خطورة هو:

- حذف الخريطة المحلية المكررة من `HeroDashboard.tsx`.
- استيراد `LEGACY_CHARACTER_MAP` المشتركة من `@/types`.
- الإبقاء على خريطة `types.ts` الحالية، بما فيها `aya: 'joud'`.
- عدم إنشاء `characterMap.ts` جديد؛ لأن الخريطة المشتركة موجودة بالفعل ويستخدمها `CharacterSelector`.
- عدم تغيير أنواع الشخصيات أو القيم المعتمدة.
- عدم تغيير سلوك القيم غير المعروفة ضمن هذا الإصلاح.

#### سلوك القيم غير المعروفة

في الأرشيف الذي تمت مراجعته، كل من `HeroDashboard` و`CharacterSelector` يتعاملان مع قيمة غير معروفة بالرجوع إلى `sham` وتحديث التخزين وفق السلوك الحالي.

لذلك يجب الحفاظ على هذا السلوك في `P3-02`. تغيير ذلك إلى No-op أو إبقاء القيمة القديمة دون تعديل سيكون تغييراً وظيفياً مستقلاً، وليس مجرد توحيد للخريطة.

#### الاختبارات

- `C152`: تحويل `aya` إلى `joud` من خلال المسارات التي تستخدم الخريطة.
- `C152b`: الحفاظ على السلوك الحالي للقيمة غير المعروفة.
- `C153–C158`: التحقق من بقية التحويلات وعدم حدوث تغيير غير مقصود في الشخصيات الحالية.
- `C158b`: التأكد من عدم إدخال اعتماد دائري جديد.

**تنبيه:** هذه النتيجة مثبتة في الأرشيف الذي فُحص، وليست تأكيداً بأن نسخة GitHub الحالية مطابقة له. يجب مطابقة الملفات الحالية قبل التنفيذ.

### 9.3 P3-03 — مراجعة دالة SQL القديمة public.mask_name

**النطاق:** قاعدة بيانات Supabase.

الهدف:

تحديد ما إذا كانت الدالة القديمة `public.mask_name` غير مستخدمة فعلاً، قبل اتخاذ قرار حذفها.

لا يجوز الخلط بين دالة SQL `public.mask_name` وبين دوال TypeScript مثل `maskName()`، ولا يجوز حذف أو تعديل دوال TypeScript ضمن هذا البند.

#### مراجعة الاستخدامات

يجب البحث في:

- ملفات TypeScript وJavaScript.
- ملفات SQL وMigrations.
- Edge Functions.
- الاختبارات والإعدادات.
- استدعاءات `.rpc()` و`rpc()`.
- النصوص الديناميكية التي قد تحتوي اسم الدالة أو تبنيه.
- `EXECUTE` و`format()` وSQL الديناميكي.
- وظائف `pg_cron` وأوامرها.
- Views وMaterialized Views.
- Triggers والدوال المرتبطة بها.
- تعريفات الدوال الأخرى في قاعدة البيانات.

البحث النصي وحده لا يكفي لإثبات عدم الاستخدام؛ يجب فحص الاستدعاءات الديناميكية والاعتماديات داخل قاعدة البيانات أيضاً.

#### شروط اتخاذ قرار الحذف

لا يتم حذف الدالة إلا بعد:

1. مراجعة الاستخدامات الثابتة والديناميكية.
2. فحص وظائف Cron.
3. فحص Views وTriggers والدوال التابعة.
4. مراجعة الاعتماديات المسجلة في قاعدة البيانات.
5. حفظ تعريف الدالة الأصلي كاملاً.
6. حفظ التوقيع وأنواع المعاملات والقيمة المرجعة.
7. حفظ المالك والصلاحيات وGRANT وREVOKE.
8. حفظ إعدادات `SECURITY DEFINER` أو `SECURITY INVOKER`.
9. حفظ `search_path` وخصائص الدالة وتعليقاتها وأي إعدادات أخرى.

إذا ثبت عدم وجود استخدام أو اعتماد، يمكن إعداد Migration مستقلة لحذف الدالة باستخدام توقيعها الدقيق ودون `CASCADE`.

لا يتم تنفيذ SQL أثناء مرحلة التخطيط.

#### خطة التراجع

يجب أن تتضمن خطة التراجع إمكانية إعادة إنشاء الدالة بالتعريف والخصائص الأصلية، ثم استعادة المالك والصلاحيات والإعدادات واختبار مسار التطبيق.

ملف Migration عكسي لا يكفي إذا لم يحتفظ بالتعريف والخصائص الأصلية كاملة.

إذا فشل التراجع، لا تتم محاولات عشوائية ولا يستخدم `CASCADE`. يتم توثيق حالة قاعدة البيانات وتحديد مسار استعادة مناسب.

#### الاختبارات

- `C159–C168`: مراجعة الاستخدامات والاعتماديات والتأكد من عدم تأثر التطبيق.
- `C169`: التحقق من عدم وجود استدعاء ديناميكي عبر Cron.
- `C170`: التحقق من عدم وجود استدعاء ديناميكي داخل SQL أو Edge Function.

يتم اعتماد قرار الحذف فقط بعد اكتمال الفحص. إذا ظهر استخدام حقيقي، لا تحذف الدالة ويعاد تصنيف البند بناءً على النتيجة.
