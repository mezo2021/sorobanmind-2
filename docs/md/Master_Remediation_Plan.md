### الجزء الأول: الهيكل الاستراتيجي والأولويات

Master Remediation Plan — SorobanMind-2

سنعتمد سجل المخاطر v2.0 بوصفه مرجع العمل لهذه الخطة. والهدف هنا ليس البدء بالإصلاح، بل تحديد ترتيب آمن يمنع أن يؤدي إصلاح مشكلة إلى إخفاء مشكلة أخرى أو إفساد جزء يعمل حالياً.

### 1\. فلسفة الترتيب (Prioritization Strategy)

### لماذا يبدأ العمل بـ P1-01؟

لأن `P1-01` يتعلق بسلامة هوية الحساب والبيانات التي تُحمّل عند الانتقال بين الحسابات، وليس بمجرد خلل في شاشة أو ميزة.

إذا لم تكن عملية اعتماد الحساب الجديد واستعادة بياناته موثوقة، فقد تحدث نتائج خطيرة:

* فتح التطبيق بعد تسجيل الدخول بحالة لا تخص الحساب الحالي.

* فقدان تقدم محلي كان ينبغي الحفاظ عليه.

* احتمال ظهور بيانات حساب سابق في جلسة حساب آخر.

* اعتماد جلسة جديدة رغم فشل استعادة بياناتها.

لذلك يجب أن تكون الأولوية هي ضمان قاعدة واحدة:

لا يُسمح للتطبيق بالانتقال إلى حالة الحساب الجديد باعتبارها سليمة قبل التأكد من نجاح خطوات اعتماد هويته واستعادة بياناته.

### لماذا لا نلمس P2 قبل إصلاح P1؟

لأن إصلاح مشكلات التخزين والعزل قبل استقرار انتقال الهوية قد يغيّر سلوك البيانات أثناء عملية تسجيل الدخول نفسها.

مثلاً، لو عدّلنا مفاتيح التخزين أو Reset أو تحميل التقدم بالتزامن مع إصلاح `adoptUser`، فقد يصبح من الصعب معرفة مصدر أي خلل يظهر:

* هل سببه إصلاح الهوية؟

* أم تعديل العزل؟

* أم تغيير سلوك إعادة الضبط؟

* أم تفاعل هذه التعديلات مع بعضها؟

نريد أن تكون نتيجة Phase 1 قابلة للاختبار والتقييم بصورة مستقلة.

### كيف نحمي التطبيق أثناء Phase 1؟

نعتمد مبدأ تجميد الملفات غير الداخلة مباشرة في الإصلاح.

| الفئة           | الملفات                                                                         | القرار أثناء Phase 1                       |
| --------------- | ------------------------------------------------------------------------------- | ------------------------------------------ |
| نطاق الإصلاح    | cloudSync.ts                                                                    | الملف الوحيد المسموح بتعديله في البداية    |
| مسار الدخول     | App.tsx، RoleSelection.tsx، AuthModal.tsx، وأي ملف يحتوي loginParent أو يستدعيه | مجمدة، إلا إذا أثبت الفحص أن تعديلها ضروري |
| التخزين والحالة | storage.ts، progressStore.ts، highScoreStore.ts، وأي Zustand store متصل بالتقدم | مجمدة                                      |
| واجهات المستخدم | GuardianDashboard.tsx، ProfileScreen.tsx، HeroDashboard.tsx                     | مجمدة                                      |
| قاعدة البيانات  | SQL وRPC وRLS وTriggers                                                         | لا تعديل                                   |

ملاحظة مهمة: لا نفترض أن كل هذه الملفات تحتاج إلى تعديل. نراجع مسار الاستدعاء أولاً، ثم نحدد بدقة إن كان الإصلاح محصوراً في `cloudSync.ts`. أي حاجة لتعديل ملف آخر يجب أن تكون مبررة ومعلنة قبل التنفيذ.

### 2\. استراتيجية الـ Commits (Commit Strategy)

لا أنصح بقاعدة «كل ملف يأخذ Commit دائماً»، ولا بقاعدة «كل مشكلة تأخذ Commit مهما كان عدد ملفاتها».

الأفضل هو:

كل Commit يمثل وحدة إصلاح مستقلة، مكتملة، وقابلة للاختبار والتراجع.

### كيف نطبق قاعدة ملف واحد → Commit → Build ناجح → الملف التالي؟

نعتمدها كقاعدة تنفيذ افتراضية، مع استثناء واحد: إذا كان إصلاح المشكلة يتطلب تعديل ملفين مترابطين ولا يمكن أن يعمل أحدهما دون الآخر، نضعهما في Commit واحد موثق بدلاً من ترك التطبيق في حالة وسيطة معطوبة.

| الحالة                         | طريقة التنفيذ                                     |
| ------------------------------ | ------------------------------------------------- |
| مشكلة يمكن إصلاحها في ملف واحد | تعديل الملف ← Commit ← Build ← اختبار             |
| مشكلة تتطلب ملفين مترابطين     | تعديل الملفين معاً ← Commit واحد ← Build ← اختبار |
| مشكلة تتطلب عدة ملفات مستقلة   | تقسيمها إلى Commits صغيرة حسب وحدات الإصلاح       |
| فشل Build                      | لا ننتقل إلى الملف أو المشكلة التالية             |
| فشل اختبار وظيفي               | نوقف المرحلة ونحدد السبب قبل المتابعة             |

### تطبيق ذلك على P1 وP2

* Phase 1: نبدأ بـ `cloudSync.ts`، ونحاول إبقاء الإصلاح في Commit مستقل واحد. إذا ظهرت ضرورة لتعديل ملف آخر، نثبت السبب أولاً.

* Phase 2: كل مشكلة عزل P2 تأخذ Commit مستقلاً متى أمكن؛ ولا نجمع مشكلتين مختلفتين لمجرد أنهما في ملفات تخزين.

* Phase 3: كل إصلاح خصوصية أو حماية يأخذ Commit مستقلاً.

* Phase 4: إصلاحات P3 والتنظيف تأخذ Commits صغيرة، ويمكن تجميع تعديلات متقاربة فقط إذا كانت وحدة واحدة واضحة.

بهذا نستطيع معرفة أي Commit أدخل الخلل، والرجوع عنه دون إلغاء إصلاحات سابقة ناجحة.

### 3\. تسلسل المراحل المقترح (High-Level Phases)

هذا هو التقسيم المقترح للعمل:

### Phase 1 — سلامة الهوية والمزامنة الحرجة

الأولوية الأولى

المشاكل التي ستحلها:

\- `P1-01` — فشل اعتماد الحساب واستعادة بياناته في `adoptUser` و`loginParent`.

الملفات المتأثرة:

* `cloudSync.ts`

* ملف أو ملفات استدعاء `loginParent`، فقط إذا أثبت الفحص ضرورة تعديلها.

### Phase 2 — عزل البيانات واستقرار التقدم

المشاكل التي ستحلها:

* `P2-03` — مخزن `srb_progress` خارج نظام العزل.

* `P2-04` — جلسات الدروس المشتركة بين Local وCloud.

* `P2-05` — أفضل نتائج لعبة الأسرار المشتركة بين اللاعبين.

* `P2-07` — Shallow Merge في `loadFromCloud`.

الملفات المتأثرة:

* `data/srb/progress.ts`

* `LessonScreen.tsx`

* `MagicSecretsScreen.tsx`

* `cloudSync.ts`

* `storage.ts`، إذا أثبتت مراجعة التنفيذ أن هناك حاجة إليه.

### Phase 3 — الخصوصية والحماية واستمرارية المزامنة

المشاكل التي ستحلها:

* `P2-01` — عدم تسجيل فشل رفع الشخصية كعملية معلقة.

* `P2-02` — بقاء الاسم الحقيقي `soroban_child_full_name` بعد Reset/Logout.

* `P2-06` — بقاء رمز Recovery PIN السابق صالحاً بعد نجاح الاسترداد.

الملفات المتأثرة:

* `ProfileScreen.tsx`

* `GuardianDashboard.tsx`

* `RoleSelection.tsx`، إذا كان مسار Logout يتطلب تعديلاً.

* `LocalPinGuard.tsx`

### Phase 4 — التنظيف والتوافق منخفض الخطورة

المشاكل التي ستحلها:

* `P3-01` — مفتاح الثيم `soroban_theme_key` دون قارئ.

* `P3-02` — اختلاف خرائط الشخصيات القديمة.

* `P3-03` — دالة `mask_name` القديمة دون اعتماديات مسجلة.

الملفات المتأثرة:

* `ProfileScreen.tsx`

* `types.ts`

* `HeroDashboard.tsx`

* قاعدة بيانات Supabase، بالنسبة إلى `mask_name`، بعد التأكد من عدم وجود استخدام غير مباشر لها.

ملاحظة: لا يعني إدراج قاعدة البيانات في Phase 4 حذف الدالة تلقائياً؛ قرار الحذف يأتي بعد مراجعة مستقلة.

### 4\. استراتيجية التراجع العامة (Global Rollback Strategy)

نعتمد Git بوصفه وسيلة التراجع الأساسية، مع الاحتفاظ بنقطة رجوع واضحة قبل بدء كل مرحلة.

### قبل بدء Phase 1

* التأكد من أن آخر نسخة مستقرة موجودة في GitHub.

* تسجيل Commit الحالي باعتباره نقطة الرجوع.

* عدم بدء أي تعديلات أخرى بالتوازي.

* الاحتفاظ بنسخة من الملف الأصلي `cloudSync.ts` للمقارنة.

### إذا ظهر خلل أثناء الإصلاح

| ما حدث                    | الإجراء                                                                      |
| ------------------------- | ---------------------------------------------------------------------------- |
| فشل Build بعد التعديل     | نوقف العمل ولا ننتقل إلى ملف آخر                                             |
| خطأ في Zustand أو التخزين | نحدد هل سببه التعديل أم مسار موجود سابقاً                                    |
| فشل تسجيل الدخول          | نوقف الاختبارات على الحسابات الحقيقية ونعود إلى نقطة الرجوع عند الحاجة       |
| ظهور بيانات حساب سابق     | نوقف اختبارات تبديل الحسابات فوراً، ولا نواصل استخدام بيانات الجلسة المتأثرة |
| فشل الإصلاح بعد Commit    | نستخدم git revert للـ Commit المعني                                          |

### لماذا `Git Revert` وليس حذف التعديلات يدوياً؟

لأنه ينشئ Commit عكسياً يحافظ على تاريخ المشروع، ويسمح لنا بمعرفة ما تم التراجع عنه ولماذا.

قاعدة أساسية: لا نستخدم Reset أو تنظيف بيانات المستخدمين كوسيلة لمعالجة فشل إصلاح برمجي. التراجع عن الكود شيء، والتعامل مع بيانات المستخدمين شيء آخر.

### 5\. سجل التبعيات (Dependencies)

### هل يعتمد P1-01 على P2-07؟

مستقلان مبدئياً

بحسب سجل المخاطر المعتمد:

| البند | الوظيفة                                                        | العلاقة                               |
| ----- | -------------------------------------------------------------- | ------------------------------------- |
| P1-01 | اعتماد هوية الحساب واستعادة بياناته عبر adoptUser وloginParent | يعالج صحة انتقال الهوية               |
| P2-07 | سلوك الدمج داخل loadFromCloud                                  | يعالج نظافة حالة البيانات عند التحميل |

هما مشكلتان مختلفتان في مسارين مختلفين، ولذلك لا نحتاج إلى إصلاح P2-07 قبل بدء P1-01.

لكن توجد علاقة اختبارية بينهما: بعد إصلاح P1-01، يجب أن نختبر تحميل البيانات في المسارات التي تستخدم `loadFromCloud`، حتى نتأكد أن الإصلاح لم يُخفِ خللاً في المسار الآخر.

### هل يجب إصلاح أي P2 قبل P1؟

لا يوجد في السجل المعتمد P2 يفرض إصلاحه قبل P1-01.

وبالتالي يكون ترتيب التنفيذ:

* P1-01 أولاً.

* اختبار انتقال الهوية واستعادة البيانات.

* اعتماد Phase 1.

* الانتقال إلى P2-03 وP2-04 وP2-05 وP2-07 ضمن Phase 2.

### خلاصة الهيكل المقترح

| المرحلة | الهدف                                 | البنود                     |
| ------- | ------------------------------------- | -------------------------- |
| Phase 1 | سلامة الهوية والمزامنة الحرجة         | P1-01                      |
| Phase 2 | عزل البيانات واستقرار التقدم          | P2-03، P2-04، P2-05، P2-07 |
| Phase 3 | الخصوصية والحماية واستمرارية المزامنة | P2-01، P2-02، P2-06        |
| Phase 4 | التنظيف والتوافق                      | P3-01، P3-02، P3-03        |

توصيتي للاعتماد: هذا التقسيم مناسب كبنية أولية للخطة، مع شرطين قبل التنفيذ:

* لا نبدأ أي P2 قبل إغلاق Phase 1 واختبارها واعتمادها.

* لا نعتبر نجاح Build وحده دليلاً على نجاح الإصلاح؛ يجب أن ينجح الاختبار الوظيفي المرتبط بالمشكلة أيضاً.

نقطة التوقف: لم نكتب كوداً، ولم نقترح SQL تنفيذياً، ولم نغيّر أي ملف. هذا هو الهيكل الاستراتيجي فقط.

بعد اعتمادك لهذا الجزء، ننتقل إلى الجزء الثاني: تفاصيل Phase 1 — خطة إصلاح P1-01 خطوة بخطوة، مع تحديد مسارات الاختبار ونقاط التوقف قبل كتابة أي كود.
