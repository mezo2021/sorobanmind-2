# P2-04 — Lesson Sessions Isolation (Design)

**التصنيف:** P2 (Medium)
**الحالة:** ✅ مغلق تصميمياً (16 نوفمبر 2026)
**المرجع:** `UNIFIED_REFERENCE.md` — قسم Phase 2
**النطاق:** `src/screens/LessonScreen.tsx` فقط (ملف واحد)
**الكود:** مؤجل إلى المرحلة 7

## 1. المشكلة الحالية

### 1.1 الجانب الأساسي: غياب العزل

المفتاح `soroban_lesson_session_${lessonId}` (في `LessonScreen.tsx:46`) يُكتب مباشرة في `localStorage` بلا بادئة `local:` أو `cloud:`.

**النتيجة:** جلسة درس بدأت في Local يمكن أن تُقرأ في Cloud (والعكس). طفلان على نفس الجهاز يريان نفس الجلسة.

### 1.2 الخلل الإضافي: `sessionLoaded` لا يُعاد تعيينه عند تغيير `lessonId`

في `LessonScreen.tsx`:
- `sessionLoaded` يبدأ `false` عند السطر 295.
- بعد أول تحميل → `true`.
- **عند تغيير `lessonId` → لا يُعاد إلى `false`.**

**النتيجة الخطيرة:** Effect الحفظ (السطر 370) يرى `sessionLoaded=true` من الدرس السابق، فيكتب **بيانات درس A تحت مفتاح درس B** قبل أن يكتمل تحميل B.

**هذا أخطر من مشكلة العزل الأصلي** — يُفسد البيانات حتى داخل نفس الوضع.

## 2. القرارات المعمارية (6 قرارات)

### D1 — العزل حسب الوضع فقط

**صيغة المفتاح:**

| الوضع | المفتاح |
|-------|---------|
| Local | `local:soroban_lesson_session_${lessonId}` |
| Cloud | `cloud:soroban_lesson_session_${lessonId}` |

**لا `userId` في المفتاح** — السبب: جلسة مؤقتة، والخلط بين طفلين على نفس الجهاز نادر ومقبول.

### D2 — لا Migration

المفاتيح القديمة (بدون بادئة) **لا تُنقل، لا تُقرأ، لا تُحذف**. تبقى Legacy مهملة.

**السبب:** لا يمكن معرفة ما إذا كانت الجلسة القديمة أُنشئت في Local أم Cloud، وإسنادها لأحدهما قد يكشف حالة طفل آخر.

### D3 — Last-Write-Wins في Cross-Tab

إذا فتح تبويبان نفس الدرس في نفس الوضع → **آخر `setItem` ناجح يفوز**.

**لا Web Locks** — لأنه جلسة تعليمية مؤقتة، لا اعتماد حساب.

### D4 — `getMode() === null` → منع التخزين

عند `null`:
- لا قراءة.
- لا كتابة.
- لا حذف.
- لا افتراض Local.
- الدرس يستمر في الذاكرة فقط (بدون استعادة أو حفظ).

**السبب:** يتفق مع قرار P2-03 (Fail-Safe، لا تخمين).

### D5 — `SessionData` بدون `version` (مؤجل)

لن نضيف حقل `version` الآن.

**السبب:** كل الحقول الحالية اختيارية (`?? default`). إضافة حقل مستقبلي لن تكسر الجلسات القديمة. نضيف Versioning فقط عند تغيير غير متوافق فعلي.

### D6 — إصلاح `sessionLoaded` عبر `loadedLessonId`

**بدلاً من Boolean، نحفظ هوية الدرس المحمّل:**

```tsx
const [loadedLessonId, setLoadedLessonId] = useState<string | null>(null);
```

في Effect الاستعادة: بعد اكتمال التحميل → setLoadedLessonId(lessonId).

في Effect الحفظ:

```tsx
if (loadedLessonId !== lessonId || !lesson) return;
```

النتيجة:

· الانتقال A → B: loadedLessonId=A, lessonId=B → الحفظ ممنوع حتى يكتمل تحميل B.
· بعد تحميل B: loadedLessonId=B → الحفظ مسموح.

لا حاجة لتعديل App.tsx (مجمّد تماماً).

3. تفاصيل الحالات (Failure Cases)

3.1 فشل setItem (QuotaExceeded)

· لا نوقف الدرس.
· لا نعرض رسالة للطفل.
· نُسجّل الخطأ في console (للتشخيص فقط).
· الدرس يستمر في الذاكرة، لكن الجلسة قد تُفقد عند الإغلاق.

المبرر: جلسة مؤقتة — أقل خطورة من بيانات التقدم.

3.2 فشل removeItem بعد إكمال الدرس

نُضيف clearSessionVerified (تحقق داخلي):

· تنفيذ removeItem.
· إعادة قراءة المفتاح — إذا لا يزال موجوداً → فشل.
· لا نوقف إكمال الدرس (اكتماله محفوظ في progressStore).
· عند فتح الدرس مجدداً → لا نقرأ جلسة قديمة.

المبرر: الحذف الفاشل يترك بيانات قديمة، لكن إكمال الدرس لا يجب أن يعتمد عليه.

3.3 وجود جلسة Local أثناء Cloud (والعكس)

· لا قراءة.
· لا كتابة فوقها.
· لا حذف.
· لا نقل.

3.4 JSON تالف

· لا انهيار.
· لا قراءة بيانات غير صالحة.
· لا Fallback إلى Legacy.
· لا حذف تلقائي.
· إرجاع جلسة فارغة للدرس الحالي.

**الحل التقني:**

```tsx

// نستخدم:

```

في Effect الاستعادة:

· بعد اكتمال تحميل الجلسة → setLoadedLessonId(lessonId).

في Effect الحفظ:

```tsx
if (loadedLessonId !== lessonId || !lesson) return;

كيف يحل المشكلة:

اللحظة lessonId loadedLessonId الحفظ
الدرس A محمّل A A ✅ مسموح
بعد الانتقال إلى B، قبل تحميل B B A ❌ ممنوع
بعد تحميل B B B ✅ مسموح

قواعد التنفيذ:

· setLoadedLessonId يجب أن يكون داخل Effect الاستعادة (لا Effect مستقل).
· Effect الحفظ يبقى منفصلاً.

النتيجة: لا حاجة لتعديل App.tsx، ولا key prop، ولا تغيير في طريقة عرض LessonScreen.

### 1\. C51 — فشل حذف الجلسة بعد إكمال الدرس

التوصية: progressStore هو المرجع الحاسم

عند فتح درس، يجب أن تكون الأولوية لحالة إكماله المحفوظة في `progressStore`:

* نتحقق أولاً هل `lessonId` موجود ضمن `completedLessons`.

* إذا كان مكتملًا، لا نعيد الجلسة المحفوظة إلى واجهة الدرس، حتى لو بقي مفتاحها في `localStorage`.

* يمكن محاولة حذف المفتاح القديم مرة أخرى كتنظيف اختياري، لكن نجاح الحذف ليس شرطاً.

* إذا لم يكن الدرس مكتملًا، نقرأ الجلسة ونعيدها بصورة طبيعية.

لماذا لا نضيف `completed: true` إلى `SessionData`؟

لأن ذلك ينشئ مصدرين للحقيقة: حالة الإكمال في `progressStore` وعلامة الإكمال في الجلسة. وقد يتعارضان إذا فشل أحد الحفظين. الأفضل أن تبقى حالة الإكمال في مكانها المعتمد، وأن تظل الجلسة مجرد بيانات استئناف مؤقتة.

تعديل C51: يفشل `removeItem` بعد الإكمال، ثم يُفتح الدرس مجدداً؛ يجب ألا تُستعاد الجلسة القديمة، ويجب ألا يتراجع الدرس عن حالة الإكمال.

### 2\. `loadedLessonId` عند `lessonId === null`

التوصية: تصفيره إلى null

عندما لا يوجد درس محدد، نضع:

`setLoadedLessonId(null)`

ولا نترك معرّف الدرس السابق.

السبب: `loadedLessonId` يعبّر عن الدرس الذي اكتمل تحميل بيانات جلسته حالياً، وليس عن آخر درس زاره المستخدم. ترك القيمة السابقة قد يسمح بمرور شرط الحفظ في حالة انتقال أو تبدل غير متوقع.

ويكون شرط الحفظ واضحاً:

* لا يوجد `lessonId`؟ لا تحميل ولا حفظ.

* `loadedLessonId !== lessonId`؟ لا حفظ.

* يتطابق المعرّفان والدرس موجود؟ يسمح بالحفظ.

وعند الانتقال إلى درس جديد، لا يُسمح بالحفظ حتى تنتهي عملية استعادة جلسته.
