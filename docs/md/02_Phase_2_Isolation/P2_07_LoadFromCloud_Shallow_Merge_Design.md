## 2. المشكلة — Shallow Merge

### س: أين يحدث Shallow Merge؟
**ج:** في `cloudSync.ts`، السطور 389–392:

```ts
useProgressStore.setState({
  ...useProgressStore.getState(),
  ...safePd,
});
```

س: لماذا هو خطر؟

المثال:

البند القيمة
الحالة المحلية قبل الاستعادة { totalXP: 1200, tickets: 8, completedLessons: ['L1','L2','L3'] }
بيانات السحابة { totalXP: 300, tickets: 2 }
النتيجة الحالية (خاطئة) { totalXP: 300, tickets: 2, completedLessons: ['L1','L2','L3'] }

المشكلة: completedLessons احتفظت بقيمتها المحلية القديمة، رغم أنها غير موجودة في النسخة السحابية. المفترض أن تأخذ القيمة الافتراضية (فارغة)، لا أن تبقى محلية.

س: هل المشكلة خطيرة اليوم؟

ج: نعم، حتى لو لم يكن هناك مستخدمون. أي مستخدم يقوم باستعادة يدوية من السحابة (زر في لوحة ولي الأمر) سيحصل على حالة ملوثة — بيانات جزئية من السحابة، جزئية من التخزين المحلي.

4. الإصلاح المستهدف

س: ما هو التسلسل المستهدف لـ loadFromCloud؟

الخطوة التفصيل
1 جلب بيانات التقدم من السحابة
2 جلب بيانات الشخصية من public_profiles
3 التحقق الأساسي من أن progress_data كائن صالح
4 التقاط Snapshot للحالة المحلية
5 useProgressStore.getState().reset()
6 تطبيق بيانات السحابة (بعد استبعاد childName و parentName)
7 تحديث هوية الشخصية
8 التأكد من نجاح التطبيق
9 return true

الترتيب مهم: reset() يحدث بعد نجاح الجلب والتحقق، لا قبلها. هذا يمنع مسح الحالة المحلية إذا فشل الجلب.

س: كيف نُعيد الحالة الافتراضية؟

نستخدم reset() الموجودة:

· الموضع: src/store/progressStore.ts:488
· السلوك: set({ ...initialState })
· مُصدَّرة: موجودة في الواجهة العامة للمتجر

لماذا لا نستخدم setState(initialState) مباشرة؟

السبب التفصيل
initialState غير مُصدَّرة نحتاج إعادة تعريفها، وهو تكرار
reset() واجهة معتمدة نحافظ على مسؤولية Zustand
الاستدعاء متزامن لا مشكلة في التحديثين المتتاليين

س: هل نحتاج تعديل progressStore.ts؟

ج: لا. reset() موجودة وكافية.

س: ماذا لو كانت النسخة السحابية {} فارغة؟

حالة progress_data القرار
صف موجود و {} نسخة سحابية فارغة صالحة → Reset إلى الحالة الافتراضية
صف موجود و null خطأ — لا يبرر مسح الحالة المحلية
صف غير موجود خطأ — لا مسح
صف موجود وبيانات صالحة تطبيق البيانات بعد Reset

لماذا {} صالح؟ لأنه كائن JSON موجود، ويعني "الحساب موجود لكن لا تقدم". يُعامل كحالة فارغة، لا كخطأ.

6. Snapshot و Rollback

س: ما الذي يجب أن يحتويه Snapshot؟

البند السبب
حالة Zustand الحالية لاستعادة الحالة عند الفشل
القيمة الخام لمفتاح cloud:sorobanmind-v2-progress لضمان تطابق الذاكرة مع localStorage
soroban_hero_key الاستعادة قد تغيّر هوية الشخصية
soroban_child_name قد تتأثر بالاستعادة

س: متى يؤخذ Snapshot؟

ج: بعد نجاح الجلب والتحقق، قبل reset(). لا فائدة منه قبل التحقق (لا شيء لتغييره)، ولا بعده (تكون البيانات قد ضاعت).

س: ماذا يحدث لو فشل التطبيق بعد بدء التعديل؟

ج: نُعيد:

1. حالة Zustand من Snapshot.
2. القيمة الخام لمفتاح التخزين.
3. soroban_hero_key.
4. soroban_child_name.

لا نكتفي بإرجاع Zustand وحده — وإلا قد تختلف الحالة في الذاكرة عن القيمة في localStorage.

س: ما المسؤول عن Rollback؟

ج: مسار الاستعادة المنسق في GuardianDashboard.tsx (حسب الملاحظة المعلقة #2). loadFromCloud() لا تعلن النجاح إلا بعد اكتمال التطبيق.

7. تجربة المستخدم (UX)

س: ما نص التأكيد قبل الاستعادة؟

عربي:

"هل تريد استعادة التقدم من السحابة؟ سيحل التقدم السحابي محل التقدم الحالي في هذا الوضع."

إنجليزي:

"Restore progress from Cloud? Cloud progress will replace the current progress in this mode."

الآلية: pickLang() (موجودة في المشروع).

س: ماذا يحدث إذا ألغى المستخدم؟

البند السلوك
استدعاء loadFromCloud ❌ لا
أخذ Snapshot ❌ لا
مسح أي بيانات ❌ لا
Reload ❌ لا

لا شيء يحدث.

س: ماذا يرى المستخدم عند النجاح؟

ج: رسالة نجاح ثم Reload (السلوك الحالي).

س: ماذا يرى المستخدم عند الفشل؟

حالة الفشل السلوك
فشل جلب التقدم رسالة خطأ، لا Reload، الحالة المحلية محفوظة
فشل جلب الملف الشخصي رسالة خطأ، لا Reload
progress_data === null رسالة خطأ، لا Reset
progress_data ليس كائناً رسالة خطأ، لا Reset
فشل أثناء التطبيق Rollback، رسالة خطأ، لا Reload
فشل Rollback نفسه خطأ واضح + عدم ادعاء النجاح

8. حالات الفشل

س: ما التفاصيل الدقيقة لكل حالة؟

الحالة السلوك
فشل جلب progress_data الاحتفاظ بالحالة المحلية
صف soroban_progress غير موجود الاحتفاظ بالحالة المحلية
progress_data === null رفض الاستعادة، لا تغيير
progress_data ليس كائناً رفض قبل Reset
فشل جلب public_profiles الاحتفاظ بالحالة المحلية
فشل reset() أو تطبيق البيانات Rollback من Snapshot
فشل حفظ الحالة في localStorage Rollback للحالة والمفتاح
فشل تحديث هوية الشخصية Rollback للحالة والهوية
نجاح كل الخطوات اعتماد + رسالة نجاح + Reload

س: لماذا نجلب الملف الشخصي قبل Reset؟

ج: لتجنب هذا السيناريو:

1. نمسح التقدم المحلي.
2. نكتشف أن طلب public_profiles فشل.
3. نترك المستخدم بحالة فارغة رغم فشل الاستعادة.

قاعدة: كل عمليات القراءة والتحقق قبل أي تعديل.

س: ما حدود التحقق من البيانات؟

ج: لا نُدخل Schema Validator كامل في P2-07. نكتفي بالتحقق الأساسي:

الفحص المطلوب
progress_data هو كائن JSON صالح نعم
ليس null نعم
ليس مصفوفة نعم
ليس قيمة بدائية نعم

Schema Validator الكامل: مؤجل إلى بند مستقبلي.

9. الاختبارات (C82 – C99)

# السيناريو النتيجة المطلوبة
C82 Cloud لا يحتوي completedLessons، المحلي يحتويها بعد الاستعادة: القيمة الافتراضية، لا القيمة المحلية
C83 Cloud يحتوي قيماً صالحة 0 و false الاحتفاظ بها، لا استبدالها افتراضياً
C84 Cloud يحتوي {} Reset إلى الحالة الافتراضية عند التأكيد
C85 فشل طلب soroban_progress الحالة المحلية لا تتغير
C86 لا توجد نسخة سحابية لا Reset، لا فقدان
C87 فشل طلب public_profiles لا Reset، لا فقدان
C88 progress_data تالف أو ليس كائناً رفض قبل التعديل
C89 المستخدم يلغي التأكيد لا استدعاء، لا تغيير، لا Reload
C90 فشل أثناء تطبيق بيانات Cloud Rollback كامل
C91 فشل حفظ مفتاح Zustand بعد Reset Rollback
C92 فشل تحديث هوية الشخصية Rollback للحالة والهوية
C93 الحساب نفسه + استعادة يدوية الاستعادة تستبدل بعد التأكيد
C94 الحساب نفسه + تسجيل دخول عادي P1-01 يحافظ على LOCAL WINS
C95 استعادة ناجحة اكتمال + رسالة نجاح + Reload
C96 فشل أي مرحلة لا رسالة نجاح، لا Reload
C97 فشل Rollback نفسه خطأ واضح، لا ادعاء تراجع
C98 ضغط زر الاستعادة مرتين متتاليتين منع تنفيذ عمليتين متداخلتين
C99 حقول متداخلة (مثل stats) البيانات بعد الاستعادة = بيانات Cloud، لا مزيجاً

س: ما الذي يختبره C99 بالتحديد؟

ج: إذا احتوت السحابة على كائن stats، يجب أن تكون بياناته بعد الاستعادة بيانات السحابة بالكامل، لا مزيجاً من خصائص محلية قديمة. هذا يثبت أن الاستعادة لا تعتمد على محتوى محلي سابق.

س: لماذا C98 (نقر مزدوج)؟

ج: لمنع تنفيذ عمليتي استعادة متداخلتين. إذا ضغط المستخدم الزر مرتين بسرعة، يجب:

· الاستعادة الأولى تبدأ.
· الثانية تُمنع (disable الزر، أو إشارة inProgress).

لم يُحسم بعد: هل نستخدم Lock (مثل adoptionInProgress في P1) أم مجرد disable UI؟ يحتاج اعتماداً.
