# P2-06b — حماية `saveNewPin` من الكتابة الجزئية

> **الحالة:** ✅ مغلق تصميمياً
> **النطاق:** ملف واحد — `src/components/LocalPinGuard.tsx`
> **الاختبارات:** C139–C145
> **ترتيب التنفيذ:** Commit مستقل بعد P2-06

---

## 1. الوضع الحالي

### س: كيف تعمل `saveNewPin` حالياً؟
**ج:** تكتب عدة مفاتيح متتالية:
1. `pinHash`
2. `pinSalt`
3. `recoveryHash` (جديد)
4. `recoverySalt` (جديد)

**بدون أي ذرية.** إذا فشلت الكتابة في منتصفها:
- بعض المفاتيح مكتوبة.
- بعضها غير مكتوب.
- **النتيجة:** حالة PIN غير متسقة.

### س: لماذا هذا خطر؟
- قد يجد المستخدم نفسه بـ PINHash جديد + salt قديم → PIN لا يعمل.
- أو PINHash جديد + recoveryHash قديم → رمز استرداد لا يطابق.
- **لا يظهر أي خطأ.**

---

## 2. القرارات المعتمدة

| # | القرار |
|---|---|
| D14 | Commit مستقل بعد P2-06 |
| D17 | التقاط Snapshot لكل مفاتيح PIN والاسترداد قبل الكتابة |
| D18 | الكتابة بترتيب محدد |
| D19 | عند الفشل: محاولة Rollback كامل |
| D20 | عدم إظهار نجاح إذا فشل Rollback |
| D21 | لا إعادة إحياء `recoveryToken` المستهلك (P2-06) |

### س: كيف نحمي العملية؟

**التسلسل:**
1. قراءة PINHash + PINSalt + recoveryHash + recoverySalt الحالية (Snapshot).
2. كتابة PINHash الجديد.
3. كتابة PINSalt الجديد.
4. كتابة recoveryHash الجديد.
5. كتابة recoverySalt الجديد.
6. التحقق من كل الكتابات.

**عند فشل أي خطوة:**
1. Rollback: إعادة PINHash + PINSalt من Snapshot.
2. إزالة أي recovery جديد كُتب جزئياً.
3. **لا إعادة إحياء recoveryToken المستهلك في P2-06.**
4. عرض خطأ.

**عند فشل Rollback نفسه:**
- رسالة صريحة: "حالة التخزين غير مؤكدة".
- لا ادعاء بنجاح الحفظ.
- لا ادعاء بنجاح الاستعادة.
