# PROJECT_CONTROL.md

## SorobanMind-2 --- ملف قيادة المشروع وتسليم السياق

**الغرض:** حفظ حالة العمل والقرارات التشغيلية المختصرة، لتسهيل متابعة
المشروع في محادثة جديدة أو مع مساعد آخر دون إعادة نقل الخطة والشرح
الطويلين.

**قاعدة أساسية:** هذا الملف سجل متابعة وتشغيل، وليس بديلاً عن الوثائق
المرجعية أو فحص نسخة GitHub الحالية. عند ظهور تعارض، لا نخمن؛ نتحقق من
الملفات الحالية ونوثق النتيجة.

------------------------------------------------------------------------

## 1. قواعد العمل الملزمة

1.  لا يُنفّذ أي بند لمجرد وجوده في الخطة؛ كل بند يحتاج مراجعة فنية عند
    الوصول إليه.
2.  لا يُغيّر ترتيب البنود المعتمد دون توضيح السبب والحصول على موافقة
    المستخدم.
3.  لا تُفتح ملفات خارج نطاق البند الجاري إلا بعد إثبات الحاجة وشرحها
    للمستخدم.
4.  لا تُضاف إصلاحات جانبية غير معتمدة إلى مهمة محددة.
5.  لا يُكتب SQL ولا تُجرى تغييرات في Supabase دون موافقة صريحة من
    المستخدم.
6.  نجاح Build لا يثبت اجتياز الاختبارات الوظيفية أو اختبارات سلامة
    البيانات.
7.  لا يُسجّل اختبار على أنه ناجح ما لم يُنفذ فعلياً. الاختبار المتعذر أو
    غير المنفذ يبقى بهذه الحالة.
8.  عند اكتشاف خلل في تصميم بند أو تعارض بين الخطة والكود، يتوقف التنفيذ
    ويُراجع التصميم أولاً.
9.  تكون التغييرات جراحية ومحدودة، مع مراعاة أن المستخدم يعمل من هاتف
    Android باستخدام GitHub Web Editor وواجهات الويب.
10. قبل كل مجموعة تغييرات: تحديد الملفات والنطاق والهدف. بعدها مراجعة
    الفرق وBuild والاختبارات المناسبة، ثم توثيق النتيجة.
11. لا تُحذف بيانات المستخدم لمعالجة خطأ برمجي. التراجع البرمجي منفصل عن
    معالجة البيانات.
12. لا تُطلب إعادة إرسال ملفات موجودة قبل التحقق من توفرها.

## 2. بيئة المشروع

-   المشروع: **SorobanMind-2**
-   التقنية: React + Vite + TypeScript + Tailwind + Supabase.
-   المستودع المعروف: `mezo2021/sorobanmind-2`
-   النشر المعروف: GitHub Pages.
-   بيئة العمل: هاتف Android فقط؛ GitHub Web Editor وSupabase Web UI.
-   أسلوب العمل: شرح عربي واضح، خطوات عملية صغيرة، وطلب واحد في كل مرة.
-   لا يُفترض أن الأرشيف المرفوع يطابق نسخة GitHub الحالية؛ يجب التحقق
    قبل اعتماد أي نتيجة تخص الكود.

## 3. الوثائق المرجعية

تُراجع الوثائق التالية معاً عند إعداد المطابقة:

1.  `Master_Remediation_Plan.md` --- الخطة الرئيسية وترتيب البنود
    والبوابات.
2.  `UNIFIED_REFERENCE.md` --- القرارات والمرجع المعماري.
3.  `TEST_PLAN.md` --- حالات الاختبار ومعايير القبول.

هذه الوثائق مراجع تصميمية، لكن حالات التنفيذ المكتوبة فيها قد تكون
قديمة. حالة التنفيذ الصحيحة تُحدّث وفق ما نُفذ وفُحص فعلياً.

الأرشيف الذي أشار إليه المستخدم: `مراجع التطبيق ٢٠ت٢.zip`. لا تُعامل
محتوياته على أنها نسخة GitHub الحالية دون مطابقة.

## 4. سجل الحالة المعروف حتى إعداد الملف

### 4.1 Phase 1 / P1-01 --- سلامة اعتماد الهوية والمزامنة

**المؤكد من سجل العمل السابق:** - أُنجزت أجزاء A7-1 وA7-2 وA7-3. - أُنجزت
دالة `retryPendingAvatar()` وربطها بحماية القفل وفق المراجعة السابقة. -
عُدّل `adoptUser()` للاحتفاظ برمز `CloudSyncError` الأصلي عند فشل العملية،
بدلاً من تغليفه دائماً بـ `ADOPTION_FAILED` بعد Rollback ناجح. - عُدّل
`verifyOtp()` ليستخدم:
`ts   upsert(..., { onConflict: 'user_id', ignoreDuplicates: true })`
لتجنب استبدال سجل التقدم الموجود بكائن فارغ. - أُبلغ عن نجاح Build بعد
هذه التعديلات.

**تنبيه:** هذه الحالة مستندة إلى سجل المحادثة وليست بديلاً عن فحص نسخة
GitHub الحالية. يجب مطابقة الملفات الحالية قبل متابعة الاختبارات أو
تعديل الكود.

### 4.2 `AuthModal.tsx`

أرسل المستخدم النسخة المعدّلة كاملة وأكد نجاح Build. تمت مراجعتها، وكانت
النقاط التالية موجودة: - استخدام `CloudSyncError`
و`CloudSyncErrorCode`. - إزالة موافقة `agreeData` المحلية. - بقاء
موافقتي guardian وprivacy إلزاميتين، وleaderboard اختيارية. - إضافة
رسائل مترجمة لأخطاء CloudSync المعروفة. - توحيد معالجة مواضع أخطاء
المصادقة باستخدام `resolveAuthErrorMessage`. - عدم تغيير منطق OTP أو
استعادة كلمة المرور ضمن هذا التعديل.

**الاختبارات التي أكد المستخدم نجاحها:** - رفض التسجيل عند غياب موافقة
guardian أو privacy. - السماح بالتسجيل عند الموافقتين، مع ترك
leaderboard اختيارية. - التسجيل وOTP والوصول إلى الشاشة الرئيسية. -
تسجيل الدخول بكلمة مرور خاطئة وعرض الرسائل المناسبة. - استعادة كلمة
المرور/إعادة التسجيل بحسب تأكيد المستخدم.

**حدود التحقق:** ترجمة رموز CloudSync العشرة تمت مراجعتها برمجياً، لكن لم
يؤكد المستخدم اختباراً فعلياً منفصلاً لكل رمز.

**ملاحظة منفصلة مؤجلة:** ظهور اسم شخصية بالإنجليزية `Active Squirrel` في
الترحيب العربي. لا تُخلط هذه المشكلة مع إصلاح AuthModal أو P1-01.

## 5. تعارض فني مفتوح يجب حسمه قبل إعلان إغلاق Phase 1

في مراجعة سابقة لنسخة `cloudSync.ts` الموجودة داخل الأرشيف
`مراجع التطبيق ٢٠ت٢.zip`، ظهر ما يلي:

-   يوجد `authFlowInProgress`.
-   يوجد `AUTH_LOCK_NAME = 'soroban-auth-adoption'`.
-   توجد دالة `withAuthLock()` تستخدم `navigator.locks.request`.
-   تدفقات الدخول وOTP تستخدم `withAuthLock` حول خطوات الاعتماد.
-   لم يظهر في الملف الذي فُحص متغير أو حارس باسم `adoptionInProgress`.

في المقابل، اختبار **C3** في خطة الاختبار يطلب التحقق من وجود
`adoptionInProgress` ورفض العملية المتزامنة.

**النتيجة:** يوجد تعارض بين وصف الاختبار والتنفيذ الذي فُحص. لا يجوز
اعتبار C3 ناجحاً، ولا إضافة المتغير تلقائياً، قبل مراجعة التصميم ومسارات
الاستدعاء في نسخة GitHub الحالية.

كما أن اختبارات C2--C6 لا يمكن إثباتها بمجرد فتح حسابين في متصفحين
مختلفين أو الضغط السريع على الهاتف. Firefox وChrome لا يشتركان عادةً في
Web Locks الخاصة بالأصل نفسه، بينما تبويبان في المتصفح نفسه قد يشتركان
في الجلسة والتخزين؛ لذلك لا تُجرَ تجارب تبديل حسابات عشوائية قد تعرض
بيانات التطبيق للاختلاط.

## 6. المرحلة الحالية --- نقطة التوقف

**الحالة الحالية: مراجعة ومطابقة، دون تنفيذ برمجي جديد.**

المطلوب بالترتيب:

1.  مطابقة النسخ الحالية في GitHub للملفات التي تغيرت، وبالأخص
    `cloudSync.ts` و`AuthModal.tsx`.
2.  مقارنة الحالة الفعلية مع `Master_Remediation_Plan.md`
    و`UNIFIED_REFERENCE.md` و`TEST_PLAN.md`.
3.  إعداد جدول موحد يميز بوضوح بين:
    -   منفذ ومراجع.
    -   منفذ وBuild ناجح، لكن الاختبار الوظيفي غير مكتمل.
    -   غير منفذ.
    -   يحتاج إعادة تصميم.
    -   متعذر اختباره في بيئة الهاتف.
4.  حسم تعارض C3، ومراجعة قابلية تنفيذ C2--C6 ووسيلة اختبارها الآمنة.
5.  تحديث هذا الملف بعد اكتمال المطابقة، وتحديد بند واحد فقط بوصفه
    الخطوة التالية.

**لا تبدأ Phase 2 قبل إغلاق بوابة Phase 1 وفق معايير موثقة.** ولا تُعلن
Phase 1 مغلقة لمجرد نجاح Build أو نجاح اختبارات واجهة AuthModal.

## 7. طريقة مراجعة كل بند مستقبلاً

لكل بند من الخطة، أنشئ بطاقة مراجعة قصيرة تتضمن:

### أ. تعريف المشكلة

-   ما الخلل المحدد؟
-   ما الدليل على وجوده في النسخة الحالية؟
-   ما أثره على البيانات أو الوظائف؟

### ب. فحص التنفيذ الحالي

-   الملفات والدوال ومسارات الاستدعاء ذات الصلة فقط.
-   ما الذي يحدث الآن فعلياً؟
-   هل تصف الخطة الكود الحالي بدقة؟

### ج. تقييم الحل

-   الحل المقترح والبدائل.
-   المخاطر والحالات الحدية وحالات الفشل.
-   قابلية الاختبار من هاتف Android.
-   هل يتطلب التغيير موافقة إضافية أو SQL؟

### د. اعتماد النطاق

قبل التنفيذ، يُعرض على المستخدم: - الهدف المحدد. - الملفات المسموح
تعديلها. - الملفات التي لن تُلمس. - السلوك المتوقع بعد الإصلاح. -
الاختبارات المطلوبة.

لا يبدأ التنفيذ قبل موافقة المستخدم على الحل والنطاق.

### هـ. التنفيذ والتحقق

-   تعديل محدود فقط.
-   مراجعة الفرق سطراً بسطر قدر الإمكان.
-   Build بعد المجموعة المحددة.
-   تنفيذ الاختبارات المتفق عليها.
-   تسجيل النتائج الفعلية، لا النتائج المتوقعة.

### و. الإغلاق والتوثيق

يُحدّث سجل البند بحالته والأدلة، ثم يُحدد البند التالي. لا يُفتح بند آخر قبل
إغلاق الحالي أو توثيق سبب إيقافه.

## 9. ضوابط الاختبار

-   لكل اختبار: رقم، هدف، إعداد مسبق، خطوات، نتيجة متوقعة، نتيجة فعلية،
    وحالة.
-   لا تُعتبر المحاكاة الذهنية أو مراجعة الكود اختباراً وظيفياً.
-   لا يُعد الضغط السريع دليلاً على حدوث تزامن فعلي.
-   لا تُستخدم حسابات حقيقية أو بيانات أطفال لاختبارات التزامن أو
    الاستعادة.
-   عند الحاجة إلى محاكاة فشل Web Locks أو رفض القفل، تُفضّل اختبارات
    معزولة/آلية بدلاً من تعريض جلسة المستخدم وبياناته للخطر.
-   إذا تعذر تنفيذ اختبار على الهاتف، يُسجل «متعذر الاختبار» مع اقتراح
    وسيلة تحقق بديلة، ولا يُسجل «ناجح».
